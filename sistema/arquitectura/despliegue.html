Antes que funcionalidades: qué corre dónde, qué datos viven dónde, y cómo se comunican los nodos. Patrón Control Plane / Data Plane (BYOC) — el estándar B2B para "el vendor opera, los datos del cliente no salen de su red".  ·  Clic en cualquier nodo para su ficha (de NODOS.md, SSoT — drawer generado). Actualizado 2026-07-07 (CK-14/CK-15): dos binarios en el data plane (I-74/CK-07), contrato de datos diseñado (CK-08), App del Auditor (N14, CK-11).
Principio rector (state-of-the-art): el sistema se parte en dos planos. Control Plane = nuestro (lo operamos, vive el know-how, NO toca datos del cliente). Data Plane = del cliente (corre en SU red, sus datos NUNCA salen). El control plane NO está en el camino del dato; el data plane jala (pull TLS) updates/config/specs — el cliente no abre puertos. Así se logran IP protegida y soberanía de datos a la vez. Precisión firmada (2026-06-21): los datos "transitan, no persisten" — la inferencia frontier los procesa con zero-retention, jamás los almacena fuera.

✅ Decisiones de arquitectura tomadas

Decididas

  1. Patrón base = BYOC (Control Plane / Data Plane) — 2026-06-20. El vendor opera el control plane (IP); el data plane corre en la red del cliente (sus datos no salen); comunicación por pull TLS (sin puertos inbound).
  2. Runtime de agentes = HÍBRIDO — 2026-06-20. API frontier para lo server-side (Discovery, levantamiento, análisis) — Claude Code suscripción NO se multiplexa server-side (ToS). Claude Code suscripción para el dev humano en su laptop.
  3. Data Plane = configurable por cliente (on-prem O su nube) — 2026-06-20. Mismo artefacto, dos destinos.
  4. "Transitan, no persisten" — 2026-06-21. Los datos del cliente transitan a la API frontier con zero-retention + minimización; jamás persisten fuera de su red. LLM on-premise = opción futura para regulados.
  5. Dos binarios independientes en el data plane — 2026-07-02, I-74/CK-07 (Stage 4 ejecutado). DevHub (cockpit, P2) y Cockpit (directorio, P1) no comparten proceso ni código; el runtime único fue transicional.
  6. Contrato de datos DevHub→Cockpit = Pull API versionada — CK-08 (diseñado, sin código). Envelope {contract_version, data}; se implementa con el primer consumidor real (BL-18) — disciplina anti-código-especulativo.
  7. App del Auditor = subsistema propio (N14) — CK-11, incorporada al mapa en CK-14. App instalable del consultor; el método embebido viaja con nuestra persona, al cliente solo cruza el resultado.
